# A-01 — A01-SEC-01: инженерная спецификация безопасного управления устройствами
**Пакет v3.7.4 · RU · 21 ноября 2026**

> **Статус:** инженерные требования и архитектурная концепция. Это не электрический проект, не спецификация закупки, не проект автоматизации и не разрешение на подключение оборудования. Все реальные цепи, аппараты защиты, кабели, контакторы, контроллеры и монтаж определяются профильными проектировщиками.

## 1. Назначение и границы

Создать единый, понятный интерфейс, через который жильцы и персонал смогут видеть состояние и управлять только разрешёнными электронными устройствами Сферы. Телефон не должен становиться прямым пультом управления инженерной сетью здания.

Базовый путь команды:

**Телефон / PWA → защищённый шлюз доступа → локальный узел политик → контроллер соответствующей зоны → исполнительный аппарат → независимая обратная связь состояния.**

Ева может объяснять состояние, помогать найти устройство и подготовить запрос. Она не получает привилегий выше пользователя, не обходит блокировки и не принимает самостоятельных решений об отключении защитных систем.

В объём первой очереди входят только явно назначенные некритические группы: обычное освещение общественных зон, информационные дисплеи, фоновое аудио, отдельные розеточные группы мастерских после инженерного допуска и пользовательские зарядные точки. Это перечень категорий для проектирования, а не утверждение об их физическом наличии.

## 2. Классы устройств и допустимое управление

| Класс | Примеры | Удалённое управление | Условия |
|---|---|---|---|
| U1 — пользовательские | свет в личной зоне, персональные настройки интерфейса | Да, в пределах своей зоны | Авторизация владельца зоны, ручной локальный override |
| U2 — общие некритические | декоративное освещение, дисплеи, фоновое аудио | Да, по роли | Расписание, лимиты, подтверждение групповых команд |
| U3 — эксплуатационные | сервисные розетки, насосы/вентиляторы некритичных технологических процессов | Ограниченно | Только обученный персонал; наряд/режим обслуживания; локальная проверка зоны |
| U4 — критичные инженерные | основные насосы, вентиляция санитарных/технических зон, серверное охлаждение | Нет из обычного приложения | Отдельная автоматика; статус можно показывать по разрешённому интерфейсу |
| U5 — жизненно важные / пожарные | пожарная сигнализация, аварийное освещение, оповещение и эвакуация, дымоудаление, подпор, противопожарные клапаны, аварийная связь | Нет | Независимые сертифицированные системы и органы управления по проекту |

Классификация конкретной нагрузки утверждается проектировщиком и ответственным за эксплуатацию. Нельзя переводить устройство в более низкий класс только ради удобства приложения.

## 3. Роли и полномочия

- **Гость:** просмотр общедоступной информации; без команд на инженерные устройства.
- **Жилец:** устройства своей жилой зоны и разрешённые пользовательские функции.
- **Оператор:** ограниченные общие устройства по смене/зоне; команды журналируются.
- **Инженер:** диагностика и сервисные операции; опасные действия требуют местного допуска и физического подтверждения.
- **Администратор безопасности:** учётные записи, роли, ключи, политики и отзыв сессий; не получает права обходить аппаратные защиты.
- **Сервисная учётная запись:** машинный доступ с отдельной идентичностью, ограниченным сроком и перечнем устройств; запрещены общие пароли и бессрочные токены.

Администратор приложения не должен иметь возможность программно отключить независимую пожарную автоматику или снять аппаратную блокировку.

## 4. Жизненный цикл команды

1. Пользователь выбирает устройство и действие.
2. Приложение показывает понятное имя, местоположение, класс критичности и ожидаемый эффект.
3. Шлюз проверяет личность, роль, привязку устройства, срок сессии и разрешение на конкретную команду.
4. Локальный узел проверяет состояние устройства, блокировки, расписание, технический режим и наличие конфликтующих команд.
5. Для U3 требуется подтверждение персонала на месте; для U4/U5 команда из приложения отклоняется.
6. Контроллер выдаёт команду только после всех проверок.
7. Независимая обратная связь подтверждает фактическое состояние.
8. Интерфейс раздельно отображает «запрос принят», «команда отправлена», «выполнение», «подтверждено датчиком/контактом», «ошибка» или «состояние неизвестно».
9. Событие записывается в журнал с субъектом, устройством, временем, результатом и источником подтверждения.

**Важно:** успешная отправка команды не равна физическому включению/выключению. Если обратная связь отсутствует или противоречива, приложение обязано показывать «состояние неизвестно», а не придумывать результат.

## 5. Матрица безопасных действий

| Событие | Поведение приложения | Поведение локальной системы |
|---|---|---|
| Потеря интернета / облака | Показывает офлайн; новые удалённые команды недоступны | Локальные автоматические функции продолжают работу по проекту |
| Потеря связи с контроллером | Команда не считается выполненной | Не повторять бесконечно; перейти в заданное для устройства безопасное состояние |
| Датчик и обратная связь расходятся | Показать конфликт и тревогу | Блокировать опасное действие, передать сигнал оператору |
| Истекла сессия / отзыв доступа | Запретить новые команды | Уже выданные команды завершаются только по локальной логике и правилам безопасности |
| Повтор/задержка сетевого пакета | Отклонить устаревший запрос | Проверять уникальный идентификатор, срок и защиту от повторного воспроизведения |
| Аварийный стоп | Отобразить состояние, не снимать блокировку | Остановка и восстановление только по локальной процедуре |
| Обслуживание | Запретить обычные команды | Локальная изоляция, блокировка повторного включения и подтверждение персонала |
| Обнаружен пожарный сигнал | Только информирование по разрешённому каналу | Независимая пожарная автоматика выполняет утверждённую причинно-следственную логику |

Безопасное состояние не одинаково для всех нагрузок: «выключить» может быть опасно для насоса, охлаждения, вентиляции или системы защиты. Для каждого актива оно задаётся отдельным анализом риска.

## 6. Физическая архитектура и интерфейсы

Предлагаемые логические компоненты:
- мобильный клиент/PWA с защищённым хранением сессии;
- шлюз удалённого доступа без прямого входящего доступа к контроллерам из интернета;
- локальный policy enforcement point;
- сегментированная OT-сеть и отдельные зоны гостевого, пользовательского, IoT и эксплуатационного доступа;
- контроллеры, выбранные по реальным требованиям и поддерживаемым протоколам;
- исполнительные аппараты, выбранные электротехническим проектом;
- независимая обратная связь: вспомогательный контакт, датчик положения/тока или иной подходящий метод;
- локальная панель/орган управления и документированная процедура ручного восстановления;
- неизменяемый или защищённый от подмены журнал событий с синхронизацией времени.

Конкретные протоколы, модели контроллеров и типы контакторов не фиксируются до составления ведомости нагрузок, расчёта токов, анализа среды и оценки киберрисков.

## 7. Требования к безопасности и приватности

- MFA или passkeys для привилегированных ролей; привязка и отзыв устройств.
- Минимальные полномочия, отдельные учётные записи, короткоживущие токены.
- Подписанные команды, уникальный nonce/ID, временное окно, защита от повторного воспроизведения и ограничение частоты.
- Шифрование каналов и защищённый жизненный цикл ключей.
- Сегментация сети; контроллеры не публикуются напрямую в интернет.
- Подписанные обновления, инвентаризация версий и план отката.
- Журналирование доступа и действий без записи лишних персональных данных.
- Явное согласие и индикатор для функций, использующих микрофон/камеру; не использовать камеры как скрытый способ наблюдения.
- Отдельные правила хранения, срока удаления и доступа к телеметрии.
- Ева не может выдавать команду на основании догадки о намерении пользователя; перед действием требуется явный запрос и проверка прав.

## 8. Функции интерфейса телефона

Обязательные состояния интерфейса:
- «Доступно» / «Недоступно по роли»;
- «Онлайн» / «Офлайн»;
- «Запрос отправлен» / «Ожидается подтверждение» / «Подтверждено» / «Ошибка» / «Неизвестно»;
- «Заблокировано локальной автоматикой»;
- «Требуется присутствие специалиста»;
- «Обслуживание — управление недоступно».

Опасные и групповые действия требуют понятного подтверждения с перечислением затронутых устройств. Не использовать одну кнопку «Выключить всё». Не скрывать критичность, расположение или причину отказа. Доступность должна быть обеспечена с клавиатуры и экранного диктора.

## 9. Минимальная модель данных устройства

Каждый управляемый актив должен иметь:
- уникальный неизменяемый ID;
- имя, тип, зону и владельца эксплуатации;
- класс U1–U5 и обоснование критичности;
- разрешённые команды и роли;
- текущий режим: normal / maintenance / locked / fault;
- источник фактического состояния и время последнего подтверждения;
- допустимые временные окна и ограничения;
- безопасное состояние и процедуру ручного восстановления;
- связи с питающей цепью, контроллером и защитными системами;
- журнал изменений конфигурации и версий.

## 10. План реализации и критерии допуска

**S0 — инвентаризация:** перечень нагрузок, назначение, зона, токи/мощность, критичность, источник питания и владелец.

**S1 — анализ рисков:** угрозы OT/IT, последствия ошибочной команды, отказ питания/связи, конфликт автоматики и ручного управления.

**S2 — стенд без силовой нагрузки:** проверка ролей, подписанных команд, replay-защиты, отзыва сессий, журнала и обратной связи на эмуляторах.

**S3 — макет одной U2-группы:** испытание с низковольтным/изолированным стендом; затем отдельное проектное решение для реальной электрической нагрузки.

**S4 — пилот:** только после утверждения электрического проекта, схем защиты, локального управления, оценки риска и процедур эксплуатации.

**S5 — расширение:** подключать новые группы только после повторения классификации и испытаний; не переносить допуск одной нагрузки на другие.

Критерии прохождения: запрещённые команды отклоняются; права отзываются; повторные и просроченные команды блокируются; состояние не выдаётся за подтверждённое без обратной связи; потеря облака не ломает локальную защиту; ручное управление и восстановление проверены; журнал позволяет восстановить последовательность событий.

## 11. Что остаётся открытым

Не выбраны физические контроллеры, протоколы, напряжения, номиналы, защитные аппараты, топология сети, поставщики IAM, политика хранения данных и конкретные устройства. Их нельзя выбирать только по визуальному прототипу. Требуются площадка, ведомость нагрузок, расчёты, применимые нормы, специалисты по электрике/АСУ ТП/кибербезопасности и испытания.
