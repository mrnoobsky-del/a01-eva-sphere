# P0 — статический аудит производительности A-01 v4.0.0

**Дата проверки:** 24 ноября 2026 года  
**Проверяемая сборка:** `digital-twin/eva-sphere-a01-v400-primary-architecture-baseline.html`  
**Версия в репозитории:** v4.0.0, ветка `main`  
**Blob SHA исходного HTML:** `610d134a5310c0c2301995fb0d10118762bd59a4`  
**Статус:** статический анализ кода выполнен; живой WebGL/FPS замер не выполнен.

## 1. Главная находка: встроенное ограничение частоты рендеринга

В исходном коде обнаружено явное ограничение интервала кадров:

- строка 1982 определяет мобильный режим по ширине окна до 780 px **или** по наличию более одного touch point;
- строка 1996 задаёт `activeFrameInterval`: 30 FPS для мобильного режима и 45 FPS для desktop-режима;
- строка 5373 относит к непрерывному движению прогулку от первого лица, автовращение, перемещение между уровнями, полёт камеры и сервисные анимации;
- строка 5380 пропускает текущий кадр и ставит следующий `requestAnimationFrame`, пока время после последнего отрисованного кадра меньше заданного интервала.

**Вывод:** текущая логика не позволяет непрерывным анимациям и режиму прогулки рендериться с частотой 60 FPS. На практике фактическая частота зависит от частоты обновления дисплея и дискретных callback `requestAnimationFrame`; поэтому нельзя автоматически считать, что desktop всегда выдаёт ровно 45 FPS. На типичном дисплее 60 Hz проверка интервала 22,22 мс может приводить примерно к 30 кадрам/с из-за пропуска следующего callback.

Это подтверждённое ограничение в коде, но не измерение фактического FPS конкретного устройства.

## 2. Текущие адаптивные настройки качества

В блоке инициализации renderer (строки 1982–1993) обнаружено:

| Настройка | Мобильный режим | Desktop-режим |
|---|---|---|
| devicePixelRatio limit при low-power | 1.0 | 1.15 |
| devicePixelRatio limit в остальных случаях | 1.12 | 1.35 |
| Antialias | выключен | зависит от low-power |
| powerPreference | low-power | high-performance |

Классификация low-power включает `hardwareConcurrency <= 4` или `deviceMemory <= 4`; при отсутствии этих API код использует значение по умолчанию 4. Поэтому конфигурация рендера может отличаться между браузерами даже на похожих устройствах.

Эти значения фиксируем как исходные настройки. Не будем снижать разрешение, убирать сглаживание или отключать эффекты дальше только ради цифры FPS. Для цели «60 FPS без потери качества» сначала необходимо выбрать эталонный визуальный режим и сравнивать его неизменно.

## 3. Режим простоя и режим движения

Сцена использует рендеринг по требованию: если нет изменений и непрерывного движения, следующий кадр не планируется. Это полезно для снижения нагрузки в простое и само по себе не является дефектом.

Проверка 60 FPS должна выполняться во время активного движения/анимации. Подготовленный [рекордер baseline](baseline-recorder.js) запускает контролируемое автовращение и измеряет реальные вызовы `renderer.render()`.

## 4. Другие кандидаты для последующего профилирования

- В режиме прогулки выполняется проверка взгляда и объектов примерно каждые 125 мс (строка 5464); внутри неё используется рекурсивный `raycaster.intersectObjects(..., true)` (строка 4340). Это кандидат на измерение CPU-нагрузки, но не доказанное узкое место.
- Обновление положения дверей, робота и Евы выполняется в цикле прогулки (строки 5423–5464). Следует профилировать при реальной прогулке, а не оптимизировать наугад.
- Счётчики `renderer.info` доступны через `window.EVA_SPHERE.renderer`; рекордер сохраняет draw calls и количество треугольников на кадр.

## 6. Следующий практический шаг

1. Получить актуальный репозиторий целиком, чтобы локальные файлы `modules/living-world/` и другие относительные ресурсы были рядом с HTML.
2. Из корня репозитория запустить локальный сервер: `py -m http.server 8000`.
3. Открыть `http://localhost:8000/digital-twin/eva-sphere-a01-v400-primary-architecture-baseline.html`.
4. Дождаться полной загрузки модели и в Chrome DevTools Console загрузить рекордер:
   
       const s = document.createElement('script');
       s.src = 'https://raw.githubusercontent.com/mrnoobsky-del/a01-eva-sphere/main/performance/baseline-recorder.js';
       document.head.appendChild(s);

5. После загрузки скрипта выполнить:

       runA01PerformanceBaseline({ durationMs: 60000 });

6. Дождаться итогового JSON в Console, скопировать его и сохранить три прогона для каждой эталонной конфигурации.

Перед тестом вернуться в общий обзор, выйти из режима прогулки и закрыть активные демонстрационные анимации. Рекордер сам включает автовращение на время теста и восстанавливает исходные положение камеры и состояние управления после завершения.

**Ограничение рекордера:** он измеряет интервалы между фактическими вызовами `renderer.render()`, CPU-время отправки команд рендереру и счётчики Three.js. Это не прямое измерение времени исполнения GPU или подтверждение фактической презентации каждого кадра дисплеем. Для GPU-профиля отдельно использовать Chrome DevTools Performance и доступные средства диагностики устройства.
